共有ハーネス(agent-harness リポジトリ)の中身(規約・skill・スクリプト・参照ドキュメント)を変更したいときの手順。
プロジェクトに取り込む(pin を進める)だけなら手順 4 だけを行う。

## 手順

### 1. 共有かプロジェクト固有かを判断する(最初に必ず)

変更に着手する前に、`harness/docs/editing.md` の「共有かプロジェクト固有か」の判断基準を読み、その変更がどちらに属するかを決める。

- **プロジェクト固有**(そのプロジェクトの語彙・事情・コードベースに依存する)なら、共有ハーネスには手を入れず、プロジェクト側で完結させる(`PROJECT.md`・プロジェクト固有 skill 等)。
- **共有**(どのプロジェクトでも同じように使える)なら、次へ進む。

共有ハーネスには特定プロジェクトの名前・語彙・事情を持ち込まない。
例が必要なら一般的なソフトウェア開発の例で書く。

### 2. agent-harness リポジトリで Issue + feature ブランチ + PR を作る

プロジェクト側の `harness/` 配下(ベンダーコピー)を直接編集してはならない(次の sync で消える)。
変更は agent-harness リポジトリ本体で行う。

1. agent-harness リポジトリに Issue を立てる(bot スクリプト `node harness/scripts/gh/gh.mjs issue create ...` 経由。本文は stdin で渡す → `pr-workflow`「本文の渡し方」)。
2. feature ブランチを切り、変更を実装して bot 名義でコミットする(`node harness/scripts/gh/commit.mjs`)。
3. PR を作る(`node harness/scripts/gh/gh.mjs pr create ...`)。

### 3. ユーザーのレビュー・マージを待つ

共有ハーネスの変更は全プロジェクトに波及するゲーティング変更なので、マージはユーザーが行う。
エージェントは勝手にマージしない。

### 4. マージ後、各プロジェクトで取り込む

マージされたら、共有ハーネスを利用している各プロジェクトで取り込む。

1. `develop` から feature ブランチを切る。
2. `agent-harness update <rev>` を実行する(pin の更新と、`harness/`・生成物の再生成を一括で行う)。
3. 差分を確認し(意図しない規約変更が混ざっていないか)、コミットして PR を作る(→ `pr-workflow`)。

取り込みもプロジェクトごとの明示的な PR であり、自動では反映されない。
`harness/` 配下と生成物(`AGENTS.md` / `CLAUDE.md` / skills ミラー / フック設定)は直接編集せず、乖離は CI の `agent-harness check` が検出する。

## 学びの括り出し(知見の昇格)

プロジェクト側で得た学び・知見(記録は `learnings` skill で行う)を恒久ルールや skill へ昇格するときも、手順 1 の「共有かプロジェクト固有か」の判断を必ず通す。

- プロジェクト固有の学びは、常時必要なら `PROJECT.md`、特定作業のときだけ必要ならプロジェクトの `docs/harness/`、手順ならプロジェクト固有 skill へ昇格する。
- どのプロジェクトでも通用する学び(ワークフローの改善・一般的な落とし穴等)は、本スキルの手順で agent-harness へ PR を出して昇格する。

昇格したら、元のエントリを記録ファイルから削除する(→ `learnings` skill)。
