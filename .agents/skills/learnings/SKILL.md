作業中に得た学びを記録し、育った知見の昇格につなげる。
記録はローカル専用で git に共有しない。
共有されるのは昇格(恒久ルール化・skill 化)されたものだけである。
記録は気づいたそのターンの成果物として行い、「後で」に回さない。

## 何を記録するか

判断の原則は 1 つである。
**次の別の場面でも行動を変える、一般化可能な知見だけを記録する。**
その場・その成果物に閉じた指摘・修正は記録しない。

対象になるのは次のような事例である。

- ユーザーの是正・レビュー指摘のうち、嗜好・方針・判断基準として一般化できるもの
- 調査して解決した非自明な失敗(コマンド・外部ツール・環境の罠)
- 自分の知識が古かった事実(ツールの新しい仕様・API の変更)
- より良いアプローチの発見
- 同じ指摘・ミスの繰り返し(既存の記録と同じミスを含む。昇格候補の強いシグナル)

### 事例

記録する:

1. 「コミットメッセージの 1 行目はサマリーだけにして」— 全コミットに適用される書式の方針。
2. 「自明なコードコメントを書くな」— コメントの残し方の一般方針。
3. 「設計案は実装の楽さより概念の単純さで選んで」— 設計の選び方の基準(その設計自体の議論ではない)。
4. 「報告は結論から書いて」— 報告スタイルの嗜好。
5. 「PR に関係ない差分を混ぜるな」— PR の切り方の方針。
6. 「依存は増やしたくないので標準ライブラリで」(理由付き)— 依存追加への方針。
7. Git Bash から `cmd.exe /c` を呼ぶと引数がパス変換で壊れる — 調査して解決した環境の罠。再発しうる。
8. ツールに新しいサブコマンドがあり自分の知識が古かった — 知識の更新。
9. 「早期 return にして」というレビュー指摘が 3 回続いた — 単発ならその場の改善だが、繰り返しにより「早期 return を好む」というスタイルとして一般化できる。
10. 既存の記録と同じミスをまたやった — その事実自体を記録する。

記録しない:

1. 「この関数名は typo している」— その場の修正のみ。
2. 「このバグは null チェックを足して直して」— 特定問題の解法。
3. 「この PR のタイトルを X に変えて」— その場の指示。
4. 「この design doc は案 B の方がいい」— その設計自体の議論(「代替案を最低 2 つ書け」なら設計文書の作法なので記録する)。
5. 「この段落は消して」— その文書限りの編集指示。
6. 自分の書いたバグでテストが落ちて直した — 通常のデバッグで、次に活きる一般知見が無い。
7. 「この変数は `count` に改名して」— 単発の命名指示(「略語を使うな」のような規則の形なら記録する)。
8. 既に規約に書いてあることの指摘 — 新しい知見ではない(読み落としを繰り返しているなら、その事実を記録する)。

一部だけ抽出する:

- 「この README のこの節を消せ。README には手順だけを書くものだ」— 前半は場限りなので捨て、「README は手順のみ」だけを記録する。
- 「このエラーメッセージは日本語にして。ユーザー向け文字列は全部日本語ね」— 後半の一般規則だけを記録する。

## どこに記録するか

リポジトリの作業ツリーではなく git ディレクトリの内側に置く。
コミット対象にならず、どの worktree から実行しても同じファイルに解決される。

```sh
echo "$(git rev-parse --path-format=absolute --git-common-dir)/agent-learnings/LEARNINGS.md"
```

ファイルが無ければディレクトリごと作って書き始める。

## 記録の形式

1 ファイルに追記する。
1 エントリは見出し 1 行 + 本文数行に収め、書式の維持より記録することを優先する。

```md
## 2026-07-25 correction
報告は結論から書く。経過の長い説明を先に置かない。

## 2026-07-25 pitfall
Git Bash から cmd.exe /c を呼ぶと /c がパス変換で壊れる。MSYS_NO_PATHCONV=1 を付ける。
```

見出しの種別は correction(是正・指摘)/ pitfall(非自明な失敗と回避)/ update(知識の更新)/ insight(より良いアプローチ)/ repeat(繰り返しの検出)から選ぶ。
迷ったら近いものでよい。

## 昇格の提案

記録が溜まったとき、または同じ指摘・ミスの繰り返しに気づいたときは、ユーザーに昇格を提案する(昇格の実行はユーザー判断で、別ブランチ + Issue + PR で行う)。
昇格先は共有かプロジェクト固有かの判断(`harness/docs/editing.md`。skill 本文のリンクは自動で開かれないので `Read` で読む)に従って次の 3 択から選ぶ。

- 全プロジェクトに通用する → agent-harness へ Issue + PR(→ `harness-update` skill)。
- プロジェクト固有かつ常時必要 → `PROJECT.md`。
- プロジェクト固有かつ特定作業のときだけ必要 → プロジェクトの `docs/harness/` に置き、`PROJECT.md` からポインタを張る。

昇格したら、元のエントリを記録ファイルから削除する(昇格済みの記録を残すと一覧が無限に溜まる)。
