対象の design doc を **敵対的に** レビューする。
粗探しをする側に立ち、「この doc を通すべきでない理由」を能動的に探す。
問題が無ければ無いと正直に言う。
このスキルはレビュー単体で、doc を修正しない(レビュー後の修正の回し方は `design-doc`)。

## 主眼は「設計自体の妥当性」(規約遵守は前提ゲート)

規約(`harness/docs/design/README.md` / `harness/docs/design/template.md`、日本語の言葉選び・表現は `harness/docs/japanese.md`)への適合は合格の必要条件にすぎず、レビューの本題ではない。
本当に確かめるのは、**その設計が、現状からの変更として、今後のプロジェクトの基盤として妥当に立つか**である。
API 設計なら立場の違う利用者のユースケースで使い勝手をトレースし、内部設計なら性能・保守性を疑い、**問題の立て方そのもの**(そもそも要るか、別の手段で済まないか)までさかのぼって問う。

## ルールの参照先(再掲しない)

規約の本文はこのスキルに書かない。
正は `harness/docs/design/README.md` と `harness/docs/design/template.md` である。
レビュー開始前に、対象 doc 全文(セットなら全部)・この 2 つの規約・プロジェクトの設計原則ドキュメント(あれば)・対象が参照する既存 design doc・設計が触れる実コードを読む。

## 関連する doc はセットでレビューする

対象 doc が他の(とくに未承認 draft の)doc を相互参照している、または同じ設計テーマを分担しているときは、1つのセットとしてまとめてレビューする(分割粒度・doc 間整合もレビュー対象になる)。
独立した doc は単体でよい。
正: README「関連する design doc はまとめてレビューする」。

## レビューの進め方(観点を順番に別パスで適用する)

次の 5 観点を、**1観点ずつ独立したパス**として順に適用する。
1回の通読で全部を同時に見ようとしない(観点を混ぜると、どの観点でも浅くなり見落とす)。
各パスでは、その観点の「立場」に立ち切って doc を最初から最後まで読み直し、findings を書き足してから次の観点へ進む。
難所(API の中核・性能の要・メタな是非)を含む doc では、該当する観点のパスをもう一周して見落としを減らす。

### パス 1: 規約遵守(前提ゲート)

- **立場**: 規約への適合を機械的に検査する監査者。
- **判断テスト**: README / template.md の各ルールに照らして、違反を1つずつ挙げられるか。とくに: 1ファイル1意思決定・連番・ヘッダー3項目・テンプレートのプレースホルダ残り・自己完結・代替案と「なぜメイン案か」・却下/不在概念の残骸(本文の否定・対比表現を走査し、引き合いの概念がリポジトリに実在するか確かめる)・一文一行。
- **高度の検査**: 各記述に「取り違えると大きな手戻りになるか、それとも PR レビューで気づいて直せるか」を問う。後者(実装高度: 関数名・関数分割・呼び出し順・編集レシピ・変更ファイル/関数インベントリ・テストカバレッジ)は正確に書けていても指摘する。「負荷・コスト」が実装工数になっていないかも見る。
- **図の検査**: doc の文脈を一切共有しない状態で図だけを見て、何を表すか・各矢印の意味が誤読なく伝わるか。矢印の意味の混在・凡例の欠落を指摘する。

### パス 2: 設計妥当性

- **立場**: この設計を通すべきでない理由を探す敵対的アーキテクト。
- **判断テスト(メタ)**: そもそもこの設計はプロジェクトの将来に必要か。問題の立て方は正しいか。既存機構の組み合わせ・より小さい変更・やらない選択で済まないか。妥当に立たないなら reject 推奨と理由を出す。
- **判断テスト(core claim)**: 「(1) 何のためにどんな設計か」と「(2) その妥当性の判断根拠」が簡潔に筋を通して立つか。概要 10〜20 行で (1) が読み取れるか。(2) の不足(簡潔さを口実にした削りを含む)は must-fix 級。(1)(2) に寄与しない水増し・同じ根拠の複数セクション反復・運用判断の混入も指摘する。
- **判断テスト(性能・保守性・シンプルさ)**: hot path・繰り返し実行されるコスト・メモリ・スケールで性能が出るか。「上乗せは小さい」等の主張が測定可能な形で立っているか。結合度・概念の増え方は長期保守に耐えるか。simple over easy(構造的な絡みを増やして easy を足していないか)。概念数・認知負荷・初見の学習コストは妥当か。
- **判断テスト(原則)**: プロジェクトの設計原則ドキュメント・API 方針(あれば)への整合を敵対的に検証する。

### パス 3: 利用者の使い勝手

- **立場**: この設計の API・機能で実際にコードを書く利用者。
- **判断テスト**: 実際のユースケース(実在の examples があればそれ、無ければ現実的なユースケース)をこの設計でどう書くことになるかを具体的にトレースし、書きにくさ・冗長・驚き・誤用しやすさ・ハックの要否を評価できるか。
- 低レベル制御が要る利用者の立場でも見る: 必要な下位レイヤの機能に到達できるか、抽象が下位へのアクセスや制御の細かさを塞いでいないか、下位概念との対応が見通せるか、ボイラープレートが過大でないか。
- doc のコード引用・シグネチャ・定数値が実コードと一致するかも検証する。

### パス 4: 実装可能性

- **立場**: この doc を渡されて実装を任される実装者。
- **判断テスト**: doc の決定だけから実装に着手できるか。決定が現実のコードベースで実現可能か(既存の型・境界・制約と衝突しないか)。失敗モード・エッジケース・拡張性の限界が「落とし穴」章に誠実に書かれているか。複数コード箇所にまたがる不変条件の単一出所の配置が design 判断として書かれているか(欠落は不足)。
- 文脈ゼロの読者としても読む: 既存の実装・挙動・プロトコル・ビルド基盤を変更する doc で、既存挙動の存在理由(その形を強いている制約)が本文だけで読み取れ、変更の是非を doc 単体で判断できるか。additive・自明な doc への過剰要求はしない。

### パス 5: 整合性

- **立場**: プロジェクト全体の一貫性を守る番人。
- **判断テスト**: 他の design doc との矛盾は無いか。共有する概念・型・契約の食い違い、境界の隙間(どの doc も書いていない)や重複(複数 doc が別々に書いている)、相互参照の正しさ。
- セットのときは分割粒度も見る: 境界の引き方は妥当か。統合・再分割した方がよくないか。詰め込みすぎ/割りすぎはないか。

## findings の形式

各指摘を次の形式で列挙する。

- **severity**: `must-fix`(承認前に必ず直す)/ `should-fix`(直すべきだが承認を止めない)/ `nit`(好みの範囲)。確証の無い推測を must-fix に上げない。
- **kind**: `design`(決定・構造・スコープの再検討を要する。表現を直しても解けない)か `writing`(表現・構成・規約適合の修正で足りる)。
- **観点**(パス 1〜5 のどれか)・**対象 doc のパス**・**位置**(セクション/行)・**問題**・**修正案**。

設計妥当性の指摘は「規約違反」ではなく「設計としてどう立たないか」を述べる。

## reject の扱い

レビューは reject を推奨できる(findings と併せて理由を述べる)。
`rejected` への確定は原則ユーザーの仕事で、`## 却下理由` セクションの書き方は README「reject 時の却下理由セクション」に従う。

## 単体で使うときの出力

`design-doc` を経由せず単体で使うときは、findings を severity 順に整理してユーザーに報告し、最後に総評(このまま承認に出してよいか、must-fix があるか、設計として立つか・reject 推奨か)を述べる。
問題が無ければ「指摘なし」と明記する。
