# コードコメントの規約

このドキュメントは **ソースコードのコメントを書く・編集するとき** に読む。
言語を問わず、リポジトリのすべてのコードコメントに適用される。
ここで定めるのは **コメントに何を書くか** である。
コメントの言葉選びと表現は [japanese.md](japanese.md)、設計判断そのものの残し方は [design/README.md](design/README.md) が定める。

## 書いてよいのは、コードだけでは読み取れない意図に限る

判断の基準は「このコメントを消したら、コードを読む人は何を失うか」である。
失うものが、コードを読めば分かることと design doc を読めば分かることだけなら、そのコメントを書かない。

## design doc の設計判断をコードへ書き写さない

design doc に書いた設計判断・その根拠・検討したトレードオフを、コードのコメントへ転記しない。
理由は 3 つある。

- **転記は追随しない。** 設計を変えるときは新しい番号の design doc で意思決定を上書きするが(→ [design/README.md](design/README.md))、コードに散らばった転記はその更新から取り残される。設計が覆された後も、古い設計を主張するコメントがコードに残る。
- **決定の所在が二重になる。** 設計判断を 1 か所に集めるために design doc を運用しているのに、同じ内容がコードにもあると、どちらが正なのかを読み手が判断できなくなる。
- **コードを読む助けにならない。** そのコードの意図を説明しているのではなく doc の要約を貼っているだけなので、コードを読む人にとって新しい情報が増えない。

### design doc に触れてよい場合

コメントから design doc に触れてよいのは、**そのコードが一見すると不自然で、注釈が無ければ「直すべき不備」と誤解されて壊される恐れがあるとき** に限る。
このとき書くのは、なぜその形なのかの短い理由と、必要なら doc への参照だけである。
doc の内容を要約して書き写さない。

## 例

悪い例(design doc に書いた設計判断と根拠を、そのままコードへ転記している):

```ts
// 受信したイベントは 1 件ずつ順番に処理する(0007「イベント処理の設計」)。
//
// 並列に処理すると、同じ対象への更新が到着順と異なる順序で適用されうる。
// この経路はスループットよりも順序の一貫性を優先するため、逐次処理にする。
for (const event of events) {
  apply(event);
}
```

良い例(コメントを消す。コードは何をしているかを自分で語り、なぜその設計かは design doc が持つ):

```ts
for (const event of events) {
  apply(event);
}
```

良い例(コードが一見して不自然で、注釈が無いと不備と見なされて消されるため、短い理由と参照だけを書く):

```ts
// 最初の読み取りは結果を捨てる。この API は接続直後の 1 回だけ古い値を返す
// (→ docs/design/0007_event_processing.md)。
await client.read();
const value = await client.read();
```
