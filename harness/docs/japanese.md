# 日本語の言葉選びと表現の規範

このドキュメントは **日本語の文章を書くとき** に読む。
design doc・参照ドキュメント・README・skill 本文・PR/Issue の本文とコメント・レビュー返信・コミットメッセージの本文・ソースコードのコメントなど、書く場所を問わずすべての日本語に適用される。
まとまった技術文書の段落構成・整形・論証は `japanese-tech-writing` skill が定め、本ドキュメントは単語の選び方と表現を定める。

## 原則: 読者に推測と解釈の負荷をかけない

以下のルールはすべて次の原則から導かれる。
**読者が想像で補わなければならない文脈を増やさず、解釈にブレが生じない言葉を選ぶ。**
列挙されていない表現でも、この原則に反するなら使わない。
個別のルールで迷ったときも、この原則に立ち返って判断する。

## 概念の名前には慣例的な技術用語だけを使う

技術概念の名前には、その分野の技術文書で慣例的に使われる用語(カタカナ語・英語をそのまま含む)だけを使う。
一般的な日本語の言葉に、ことわりなく特別な技術的意味を持たせて概念名として使わない。
定義していない言葉で概念を指すことになり、読者は一般的な意味との違いを推測しながら読まされるからである。

悪い例と言い換え(実際に指摘された例):

- 「台帳」(帳簿・会計の言葉)→ 記録ファイル、一覧、ログなど、実体をそのまま言う。
- 「正典」(宗教・文学の言葉)→ 「正とする」「〜が正」、または対象を直接指す。
- 「一般語」「術語化」のような、日本語として一般的でない熟語の発明 → 「一般的な言葉」「技術用語として使う」のように普通の言い方で書く。

漢字の熟語を組み合わせて新しい概念名を作ることもしない(中国語の語彙のように見え、日本語の技術文書の語感から外れる)。
複数のドキュメントをまとめて指す名前が必要な場合も、名前を発明せずに対象を直接列挙して参照する(名付けがどうしても必要なら、個別のドキュメントや skill の内部ではなく常時規約のようなプロジェクトレベルの場所で定義する)。

## 一つの言葉を複数の意味に転用しない

より適切な個別の日本語表現があるのに、便利な一語へ意味の違う用法を集約しない。
一語に複数の意味を負わせると、その語がその文脈でどの意味なのかを読者がその場で判断させられ、誤解の余地が生まれるからである。

実際に指摘された例が「効く」の転用である。
「同じ原則が効く」と書かれた文の意味は「同じ原則で編集を行う」だったが、「効く」は使う場所によって「有効である」「適用される」「役に立つ」「問題なく動作する」のどれの意味にもなり、読者が文脈から推測するしかない。
それぞれの場所で、そこで意味することをそのまま言う個別の表現を使う。

## 生成 AI に特有の定型表現を使わない

生成 AI が書く日本語には、内容を増やさずに形だけ整える定型表現がある。
どれも、判断をぼかす・強調するだけで中身を説明しない・自然な日本語話者が書かない言い回しで読者を引っかからせる、という形で冒頭の原則に反する。

- **判断をぼかす締め**: 「〜と言えるでしょう」「〜かもしれません」(根拠なく主張を弱める場合)。読者がどこまで確かな話か判断できなくなる。判断を明確に言い切る。
- **中身のない強調・宣伝調**: 「〜は非常に重要です」「重要なのは〜ということです」「〜を実現します」「〜が可能になります」「〜がカギです」「成功の近道です」。なぜ・どのようにを説明せず強調だけを足し、情報が増えない。内容をそのまま述べる。
- **唐突な接続**: 文頭の「だから」「なので」。話し言葉の接続であり、文章では前後の論理関係の説明を省いた印象を与える。「そのため」「したがって」を使う。
- **読者への呼びかけ調**: 「いかがでしたでしょうか」「〜を深掘りしていきましょう」。技術文書に不要な演出で、情報を持たない。
- **機械的な反復**: 同じ語尾(「です」「ます」「でしょう」)や同じ長さ・同じ構造の文の繰り返し、「〜だけでなく〜も」の多用。型で埋めた文章になり、どこが重要かが読み取れなくなる。

判断の基準は「同じ内容を日本語話者の技術者が書いたときに出てくる言い方か」である。
新しく指摘・検出された表現は、上のどの型に当たるか(またはどう原則に反するか)とともに追記する。

## 参照のタイミング

日本語の文章を書く作業の前に、このセッションで未読ならこのドキュメントを読む。

- design doc・ドキュメント・skill 本文の執筆と推敲: design-doc 系 skill と `japanese-tech-writing` skill が参照を指示する。
- PR/Issue の本文・コメント・レビュー返信・コミットメッセージ: `pr-workflow` skill が参照を指示し、bot ラッパーの実行時にフックが読むよう促す。
- ソースコードのコメント: 書くときの専用のフックは置かない。PR を出す前の見直しで、差分に入ったコメントも読み直す(→ [git-and-pr.md](git-and-pr.md)「PR を出す前に日本語を見直す」)。
