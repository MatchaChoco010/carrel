# ハーネス編集の作法

このドキュメントは **ハーネスを編集するときに読む**。
ハーネスとは、コーディングエージェント向けの恒久的な指示・規約・道具立ての総称で、具体的には次を指す。

- `harness/AGENTS.md`(共有の常時規約)とプロジェクト側の `PROJECT.md`(プロジェクト固有の常時規約)。両者を結合したルート `AGENTS.md` が生成される。
- skill(共有 skill は本リポジトリで管理し、各プロジェクトへミラーされる。プロジェクト固有 skill はプロジェクト側に置く)
- `harness/docs/` 配下の参照ドキュメント(本ファイルを含む)
- `harness/docs/design/README.md` / `template.md`(design doc のルール)
- 再利用スクリプト(共有は `harness/scripts/`、プロジェクト固有はプロジェクトの `scripts/`)

ハーネスの変更は、プロダクトコードと同じく **Issue + feature ブランチ + ゲーティング PR** で行い、マージはユーザーが行う(詳細は [git-and-pr.md](git-and-pr.md))。
本ファイルはその「中身をどう書くか」を定める。

## 1. 共有ハーネスかプロジェクト固有かの判断

編集・新設しようとしている規約・skill・スクリプトが、共有ハーネス(本リポジトリ)とプロジェクト側のどちらに属するかを、書き始める前に判断する。

1. **プロジェクト名・固有コマンド・固有ドメイン語彙を消しても成立するなら共有ハーネス。** 本リポジトリへの Issue + PR で変更し、マージ後に各プロジェクトが `.harness-version` の pin を進めて再 sync することで取り込む。
2. **プロジェクトの事実(検証コマンド、リポジトリ構成、固有ワークフロー)に依存するならプロジェクト固有。** 常時必要なら `PROJECT.md`、特定作業のときだけ必要ならプロジェクトの `docs/harness/`(`PROJECT.md` からポインタを張る)、手順なら `.claude/skills/`(共有ミラー以外の名前)に置く。
3. **迷ったらまずプロジェクト固有に書く。** 2 つ目のプロジェクトで同じ記述が必要になった時点で、共有ハーネスへ昇格する。

学び・知見を skill や恒久ルールへ昇格するときにも同じ判断を適用する。
共有側に置く文書には、特定プロジェクトの名前・語彙・固有の事実を一切書かない(例が必要なら一般的なソフトウェア開発の例を使う)。

## 2. 多ツール対応の規則

このハーネスは複数のコーディングエージェント(Claude Code / Codex / opencode など)から使われる。
指示や手順は、特定ツールの機能を前提にせず可搬な形で書く。

- **指示の正はルート `AGENTS.md`**(生成物。ソースは `harness/AGENTS.md` とプロジェクトの `PROJECT.md`)。`CLAUDE.md` は `@AGENTS.md` の 1 行(生成物)であり、直接編集しない。
- **手順は SKILL.md 標準形式(agentskills.io)の skill として書く。** ツール固有のコマンド機構(Claude Code の slash commands 等)に依存しない。skill の中でツール固有機能に触れる必要がある場合は「Claude Code では〜、それ以外では〜」の分岐を明記する。
- **フックはハンドラを共有し、登録は sync が全ツール分を生成する。** ハンドラスクリプトは `harness/scripts/hooks/` に置き(stdin の JSON を読み、deny は `hookSpecificOutput.permissionDecision` で返す)、各ツールへの登録設定(Claude Code `.claude/settings.json` / Codex `.codex/hooks.json` / opencode `.opencode/plugins/agent-harness.js`)は sync(`agent-harness sync`)が生成・マージする。sync が管理するのは command に `harness/scripts/hooks/` を含むエントリだけで、プロジェクト独自のフックや permissions を同じ設定ファイルに追記しても保持される(opencode は別ファイルのプラグインとして追加する)。

## 3. ベンダー領域の編集禁止

消費側プロジェクトの `harness/` ディレクトリは sync スクリプトが管理する生成物であり、直接編集してはいけない(フックが検知し、CI の `--check` が落とす)。
共有ハーネスを変えたいときは、本リポジトリへの Issue + PR で変更し、マージ後にプロジェクト側で pin を進めて再 sync する。
ルート `AGENTS.md` と `CLAUDE.md`、skills のミラー(`.claude/skills/` と `.agents/skills/` の共有分)も同じく生成物なので直接編集しない。

## 4. 既存を読み、マージ・整理してから書く(継ぎ足し禁止)

ユーザーの指摘やフィードバックを反映するとき、**該当箇所の末尾に新しい段落を継ぎ足すだけ**にしない。
継ぎ足しを繰り返すと、ハーネスは整理されないまま冗長に伸び、同じ話題が複数箇所に分散し、読み手(=次にそれを使うエージェント)が一意に読み取れなくなる。

加筆・修正の前に必ず次を行う。

1. **既存のハーネス全体の関連箇所を読む。** 加筆しようとしている内容が、既にどこかで(AGENTS.md・別の skill・別の `harness/docs/`)語られていないかを確認する。
2. **重複・近接する記述はマージする。** 同じ規則を 2 か所に置かない。既存の記述に統合できるなら、新しい節を足すのではなく既存の節を書き直して取り込む。
3. **整理してから書く。** 追記後の文書が、最初から一貫して書かれたかのように読める状態にする。「あとから足したパッチの層」に見える状態にしない。節の順序・見出し・粒度を必要なら組み替える。
4. **一意に読めるか確認する。** 誤読の余地がある表現、複数の解釈ができる指示を残さない。skill は再現性が命なので、読み手によって挙動が変わる書き方をしない。

目安: 「この変更で文書は短く・明確になったか、それとも長く・散らかったか」を自問する。
後者なら整理し直す。

## 5. 常時規約の整理の規律 — 常時必要な規約だけを置く

ルート `AGENTS.md`(= `harness/AGENTS.md` + `PROJECT.md`)は **毎セッション常に読み込まれる**。
そのため、そこには**事実上どの作業でも関係する standing な規約(ゲート)だけ**を置く。
特定の作業のときにしか要らないルールを常時規約に書かない。

加筆先を決める判断基準:

- **常時必要(ほぼ毎タスク関わる)** → `harness/AGENTS.md`(共有)または `PROJECT.md`(固有)に、既存と**マージして**置く。例: 誰が何をマージするか、PR はレビュー単位、ハーネスも Issue+PR。
- **特定作業のときだけ必要(条件付き)** → **on-demand ドキュメント(共有は `harness/docs/`、プロジェクト固有はプロジェクトの `docs/harness/`)または skill** に置き、常時規約からは**短いポインタ 1 行**で参照する。例: scripts の書き方(→ [scripts.md](scripts.md))、Issue/PR の詳細手順(→ [git-and-pr.md](git-and-pr.md) / `pr-workflow` skill)、ハーネス編集の作法(本ファイル)。

「念のため常時規約に書いておく」をしない。
条件付きルールを常時規約に積むと、毎セッションのコンテキストを食い、本当に常時必要な規約が埋もれる(結合後の AGENTS.md はツールによってサイズ上限で切り詰められることもある)。
迷ったら「この規則は、これと無関係な作業をしているエージェントにも読ませる価値があるか」を問う。
無ければ on-demand 側に置く。

参照ドキュメントを新設したら、常時規約(または親の skill/doc)にポインタを張り、[README.md](README.md) の索引に「いつ読むか」とともに登録する。
ポインタは「いつ読むか」が分かる 1 行にする(例:「scripts を書くときは [scripts.md] を読む」)。
ただしポインタを張るだけで終わらせず、**読まれる仕組み**まで用意する(§8)。

## 6. skill も同じ — 1 つの skill に無関係な条件を積まない

skill も同じ原則で編集する。
ユーザーの指摘が来るたびに 1 つの skill の末尾へ無関係な条件を継ぎ足さない。
skill は単一の役割に閉じ、その役割に必要なことだけを、整理された形で持つ。
別の関心事が育ってきたら、別の skill か参照ドキュメントに分ける。
skill 間で重複する手順は一方を正にしてもう一方からポインタで参照する(例: `pr-workflow` skill は方針の正を [git-and-pr.md](git-and-pr.md) に置き、自身はコマンド手順に徹する)。

## 7. skill 本文から repo 内の文書を指すポインタ

skill の `SKILL.md` 本文は、skill 起動時にそのまま**コンテキストへ展開される**(ファイルとして開かれるのではない)。
本文中の markdown リンクは**自動で解決・ロードされない** — リンク先の中身が要るときはエージェントがファイル読み取りで開く。
したがって skill から repo 内の文書を指すときは次のようにする。

- **パスはリポジトリルート起点**で書く(例: `harness/docs/git-and-pr.md`)。エージェントの cwd はリポジトリルートなので、この形なら確実に開ける。`../../../docs/...` のような **SKILL.md 位置を基点とする相対パスは使わない**(基点が曖昧で脆い)。リンクにするなら表示テキストも href もルート起点に揃えるか、いっそインラインコードのパスで書く。
- **常時規約(AGENTS.md)は常にコンテキストにある。** そこから既に辿れる文書を、skill 側でわざわざ deep-link して重複させない。「方針の正は AGENTS.md『…』と、そこから辿る `harness/docs/...`」と参照し、skill 自身を冗長なリンク集にしない。
- skill **同梱**のファイル(`references/` 等)を参照するときは、skill ディレクトリからのパスであることを明記する。ツール固有の解決変数(Claude Code の `${CLAUDE_SKILL_DIR}` 等)を使う場合は「Claude Code では〜、それ以外では skill ディレクトリからの相対で解決する」の分岐を書く(§2)。

(人間や markdown ビューアが**ファイルとして**読む `docs/**` 同士のリンクは、通常どおり相対リンクでよい。上記は実行時に展開される skill 本文に限った注意である。)

## 8. ハーネスは「読まれる仕組み」まで作る(完了の定義)

参照ドキュメントや skill を新設・変更したら、**それが必要なときに実際に読まれるところまで用意して初めて「完了」**とする。
「詳細はここ」と受動的なポインタを置くだけでは、いつ読むか・読まねばならないかが曖昧で、結局読まれない。
次をすべて満たす。

1. **いつ読む/読まねばならないかを明示する。** 何の作業のときに必須なのかを、ドキュメント冒頭と索引([README.md](README.md))に書く。
2. **索引に登録する。** [README.md](README.md) の一覧表に、ドキュメントと「読むべきタイミング」を追加する。一覧から漏れた文書は存在しないのと同じになる。
3. **読まれる仕組み(トリガー)を用意する。** 受動的なポインタに頼らず、次のいずれかで発火させる。
   - **作業内容で発火する規約**(Issue/PR、design doc、テスト戦略など)→ その作業を `description` でトリガーする **skill**(`pr-workflow`・`design-doc` 系など)から参照させる。skill 本文は起動時にコンテキストへ読み込まれる。
   - **特定のファイル操作で発火する規約**(ハーネス編集など)→ **フック**でリマインダーを注入する。ハンドラスクリプトは `harness/scripts/hooks/` で共有し、各ツールへの登録設定は sync が生成する(§2)。フックが効かないツール・環境でも成立するよう、常時規約のポインタと索引の記述だけで足りる状態も保つ。
   - **事実上どの作業でも必要なゲート**だけ常時規約(AGENTS.md。常時ロード)に置く。
4. **発火を確認する。** フックなら実際に動かして注入されること、skill なら description が想定タスクでトリガーすることを確かめる。

ドキュメントやスキルを足す変更には「正しく使われるようにセットアップする」ところまでを必ず含める。
セットアップ(索引登録・トリガー・発火確認)を伴わない規約追加は未完成とみなす。

## 9. SKILL.md は「指示書」— 実行することだけを書く

`SKILL.md`(スキル本体)は、起動したエージェントに **何をどう実行してほしいかの指示** を書く文書である。
一般的な解説ドキュメントではない。
次を SKILL.md に書かない。

- **設計判断の理由・正当化。** 「なぜこの方式にしたか」「なぜ別案でなくこれか」「移植性のため」といった、そのスキルをそう作った理由は SKILL.md に書かない(design doc / PR / コミットに書く)。SKILL.md には結論=「こう実行する」だけを書く。
- **過去の状態・変更の経緯・差分。** 「以前は X だった」「当初は Y を使ったが Z に変えた」は書かない。現在の指示だけを書く(履歴は Git が持つ)。これは SKILL.md に限らず、現状を説明する**すべてのハーネス文書**(`harness/docs/` 等)に共通する。
- **実行に不要な関連情報の寄せ集め。** 別スキルの使い分け説明など、いまそのスキルを実行するのに要らない情報を混ぜない(例: あるスキルの指示の中で、別スキルをいつ使うかを併記しない)。
- **書式・フォーマットの指示は具体例で示す。** 抽象的な説明でなく実際の記述例を載せる(「N と回答内容」ではなく「`4: 実際の回答をここに書く`」のように)。

迷ったら「これはこのスキルを実行するエージェントが、実行のために読む必要があるか」を問う。
理由・経緯・他スキルの紹介・抽象説明だけ、はいずれも不要。
なお、役割が近いスキルを作り分ける前に、**既存スキルに文脈を足して使えば足りないか**を必ず検討する(分ける意味が無ければ分けない。分けるなら各スキルの `description` でどちらを使うかが一意に分かるようにする)。

## チェックリスト(ハーネス編集を終える前に)

- その変更は共有ハーネスとプロジェクト固有のどちらに属するか判断したか(§1)。共有側に特定プロジェクトの名前・語彙を書いていないか。
- 消費側プロジェクトの `harness/`(ベンダー領域)を直接編集していないか(§3)。
- ツール固有機能への依存を持ち込んでいないか。持ち込むなら分岐を明記したか(§2)。
- 加筆内容が既存のどこかと重複していないか。重複は 1 か所に統合したか。
- 追記後の文書は、継ぎ足しの層ではなく一貫した 1 本の文書として読めるか。
- 常時規約に足したものは、本当に常時必要な standing 規約か(条件付きなら外出ししたか)。
- 新設/変更したドキュメント・skill を [README.md](README.md) の索引に「いつ読むか」付きで登録したか。
- 受動的なポインタで終わらせず、読まれる仕組み(skill の description / フック / 常時規約のゲート)を用意し、発火を確認したか(§8)。
- SKILL.md に、設計理由・過去の状態/差分・他スキルの紹介など実行に不要な情報を書いていないか。書式の指示は具体例で示したか(§9)。役割が近いスキルを新設する前に、既存スキル + 文脈で足りないかを検討したか。
- 誤読の余地がなく一意に読めるか。
