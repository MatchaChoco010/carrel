design doc を **執筆 → 敵対的レビュー → 指摘反映** のラウンドで仕上げ、must-fix が出なくなった `ready for review` の完成品をユーザーに提示する。
敵対的レビューは AI による品質ゲートであり、人間レビュー(レビュー PR)を置き換えない。
最終承認(`approved` / `rejected` の確定)は必ず人間が行う。

このスキルは収束ラウンドの回し方を定める。
執筆の手順(設計案の比較・骨子の形式・完成チェック)は `harness/skills/design-doc-write/SKILL.md`、レビューの手順(観点別パスと findings の形式)は `harness/skills/design-doc-review/SKILL.md` にあり、必要な時点で Read して使う。

## 全体フロー

1. **執筆前のすり合わせ。** 記録する意思決定を1つに定め、目的・解くべき問題・スコープの外枠をユーザーとすり合わせる(曖昧なら `grilling` で1問ずつ)。書き始めた後は、初稿が完成するまで設計判断・分割・スコープをユーザーに仰がない(正: `harness/docs/design/README.md`「初稿は執筆側が完成させる」)。
2. **初稿の執筆。** `design-doc-write` の手順に従う(設計案の列挙と敵対的比較 → 骨子確定 → 骨子に沿った執筆)。骨子ファイルは収束ラウンドでも使うので残す。
3. **収束ラウンド(下記)。** must-fix が出なくなるまで回す。
4. **仕上げ。** status を `ready for review` にし、INDEX.md を更新し、`feature/design-<topic> → develop` を `--no-ff`(PR なし)で landing する(`harness/docs/git-and-pr.md`「Design Doc のブランチ運用」)。
5. **レビュー PR。** landing に続けて `pr-workflow`「Design Doc レビュー PR」でレビュー PR を立て、各ラウンドの指摘と対応の要約とともに PR の URL をユーザーに伝える(以降のマージはユーザー)。`draft` のまま執筆を中断するときは landing だけで止め、レビュー PR は立てない。

既存 doc のレビュー+修正から始める場合は、まず対象 doc から骨子(決定・代替案・セクション別の主張)を書き起こしてから、収束ラウンドに入る。

## 収束ラウンド

各ラウンドは「レビュー → 裁く → 反映」で回す。

1. **レビュー。** `design-doc-review` の手順で、5 観点を順番に別パスで適用して findings を出す。関連する draft(相互参照する/同じ設計テーマを分担する)はセットでまとめてレビューする。
2. **裁く。** must-fix / should-fix を1つずつ読み、処理を決める。
   - **kind=design(決定の反転・構造・スコープ/分割の変更を要する)**: その論点を設計原則・各案の Pros/Cons・コードベースの一貫性で **自分が再決定**し、骨子を更新する(決定を差し替えるか、指摘を退けて理由を代替案/落とし穴の主張に反映する)。doc の分割・統合が要るなら、骨子とファイル構成も自分で組み替える。
   - **kind=writing**: 修正内容を控えて反映に渡す。
   - **reject 推奨**: 自分も設計が根本的に立たないと判断したら、reject 推奨とその理由を決めた立場として doc に記録して初稿を仕上げる。ユーザーに「どうしますか」と問わない(最終 approve / reject の確定だけがユーザーの仕事)。
3. **反映。** 更新した骨子と findings に沿って doc を直す。**kind=design の must-fix を付け足し編集で直さない**(構造的な問題は骨子を直してから、影響するセクションを骨子に沿って書き直してこそ収束する。付け足しはレビュー対象面を増やして doc を肥大・発散させる)。付け足しの直接編集でよいのは kind=writing の、構造を変えない修正に限る。反映後、`design-doc-write` の「完成チェック」で通読する。
4. **終了判定とガード。**
   - must-fix がゼロになったら、should-fix / nit のうち直す価値のあるものを構造を変えずに整えて終了。
   - 最大 5 ラウンド。must-fix が2ラウンド連続で減らなければ打ち切る(機械的な再レビューでは詰め切れない合図)。
   - **打ち切りはユーザーに問う合図ではない。** 敵対的レビューは十分長い doc から常に何かを見つけるので、機械的に 0 収束しないのは正常。残る指摘は kind=design の手順(自分で再決定)で決め切り、初稿を完成させる(正: README「初稿は執筆側が完成させる」)。
   - **発散の兆候**(ラウンドをまたいで doc が膨らみ続ける・骨子に無いセクションや改名が現れる・指摘が減らない)を見たら、肥大版を磨き続けず、最後に landing した版に戻して骨子の設計方針を直してから書き直す。復元は `git restore --source=HEAD --staged --worktree -- <paths>` のように対象を名指しする(`git reset --hard` は影響範囲が広く避ける)。

## 注意

- **精度優先。** コストを理由にラウンド数・レビュー観点を勝手に削らない。
- **セットは骨子で整合を取り、執筆・反映は doc ごとに行う。** セット全体を一気に混ぜて書き直さない。
- ハーネス(このスキル等)の更新自体は Issue と PR で管理する(→ `harness-update` skill)。
